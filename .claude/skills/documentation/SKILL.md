# Написание документации

Это про **что** писать, а не **где**. Расположение документации (README, `docs/`, wiki, файлы
рядом с модулем и т.п.) в каждом проекте своё — сначала посмотри, как уже организована
документация в этом проекте (или спроси оркестратора, если её ещё нет), и следуй этому месту и
формату. Ниже — принципы содержания, применимые к любому расположению.

## Для кого пишешь

- Определи адресата документа до того, как начать писать: пользователь продукта, разработчик,
  который придёт в код через полгода, или тот, кто настраивает CI/деплой. Разным адресатам нужны
  разные детали — не смешивай "как поиграть/пользоваться" с "как устроена архитектура" в одном
  разделе.

## Что писать

- **Не пересказывай код.** Документация не должна дублировать то, что и так понятно из читаемого
  кода/сигнатур — это гниёт при первом же рефакторинге. Пиши то, что код сам по себе не
  показывает: зачем это существует, какие ограничения/компромиссы учтены, почему выбран именно
  такой подход, если это неочевидно.
- **Пиши то, что реально нужно для работы с проектом:** как запустить/собрать/развернуть, какие
  есть предпосылки/зависимости, какие есть неочевидные ручные шаги, какие команды часто
  используются. Это то, что нельзя восстановить чтением кода за разумное время.
- **Не документируй то, что должно быть очевидно из хорошего именования и структуры.** Если
  документация нужна только потому, что код непонятен — лучше сделать код понятнее, а не
  компенсировать это текстом рядом.
- **Избегай дублирования между документами.** Если факт уже описан в одном месте — ссылайся на
  него, а не копируй. Дублирование — источник рассинхронизации при будущих правках.

## Структура и формат Markdown

- Заголовки — по иерархии смысла (`#` для заголовка документа, дальше по вложенности), без
  пропуска уровней.
- Короткие абзацы и списки вместо стены текста — документ должен быть удобен для быстрого
  сканирования, а не только для чтения от начала до конца.
- Примеры (команды, фрагменты конфигурации, вызовы) — там, где текстовое описание неоднозначно.
  Пример должен быть рабочим, а не иллюстративным приближением.
- Ссылки между связанными документами вместо повторения содержимого.
- Пиши в настоящем времени и в актуальном состоянии проекта — документация описывает "как есть
  сейчас", а не историю изменений (для истории — commit-сообщения/changelog, не этот документ).

## Актуальность

- Правь документацию в том же изменении, где меняется описанное поведение — не откладывай "потом
  поправлю". Устаревшая документация хуже отсутствующей, потому что ей продолжают доверять.
- Если правка делает часть существующей документации неверной — исправь её, а не оставляй
  "как есть до отдельной задачи".
