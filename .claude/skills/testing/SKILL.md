# Написание тестов

Принципы ниже не зависят от конкретного языка/фреймворка. Выбор тест-инструмента — не предмет
этого скилла: если в проекте уже есть тест-фреймворк, используй его; если его нет, а задача
требует его ввести — согласуй выбор с оркестратором как отдельное решение, прежде чем писать
тесты.

## Юнит-тесты

- Покрывай изолируемую логику: чистые функции и модули без побочных эффектов проще всего
  тестировать (вход → выход). При написании нового кода учитывай тестируемость заранее, но не
  делай масштабный рефакторинг существующего кода ради тестируемости без отдельного запроса.
- Один тест — один сценарий/утверждение. Имя теста описывает поведение, а не реализацию.

## Интеграционные тесты

- Проверяют взаимодействие нескольких частей системы (например: ввод → обработка → изменение
  состояния → отображение результата), а не единичную функцию. Используй, когда баг возможен
  именно на стыке систем/модулей.

## E2E / смок-тесты

- Прогон реального приложения целиком — доступным для стека способом (headless-режим,
  CLI-запуск, браузерная автоматизация и т.п.) с проверкой на ошибки/креши и наблюдаемое
  поведение. Это основной способ проверить "система вообще работает целиком", особенно если
  юнит-покрытия пока недостаточно.

## Нагрузочные тесты

- Имеют смысл там, где есть реальная конкурентность/масштаб (сеть, бэкенд, множество
  одновременных пользователей/запросов). Для небольших автономных приложений без сетевой
  нагрузки обычно избыточны — в таких случаях, если это вообще релевантно, ограничивайся
  проверкой стабильности производительности при длительном использовании.

## Общее

- Пиши тест вместе с исправлением бага, чтобы зафиксировать регрессию, а не только чинить
  симптом.
- Приоритет покрытия — критическая логика, а не второстепенные детали интерфейса.
